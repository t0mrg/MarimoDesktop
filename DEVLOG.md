# DEVLOG

Append-only log of stages and key decisions. Format: `## YYYY-MM-DD — title`.

## 2026-11-04 — Project start; decisions
- Asked the user four questions. Answers: managed venv; native variable browser; macOS 26 + SwiftPM; core-workflow Git plugin.
- Toolchain: Swift 6.3.3, **Command Line Tools only (no Xcode)**, uv 0.13.6, git 2.56, Python 3.14 (miniconda). Consequence: no actool or Xcode previews, so the icon is generated by script.
- **Decision: one `marimo edit` process per tab** rather than a single multi-file server. Alternatives: a shared server with `?file=` routing (lighter, but kernels share a process tree and the variable mirror is harder to scope). Per-tab gives clean isolation and clean teardown.
- **Decision: variable browser via Marimo kiosk-mode WebSocket** (`/ws?kiosk=true`), verified present in marimo 0.25.2 source (`ws_connection_validator.py`). This replaces "kernel hook" injection with an official mirroring mechanism, with no patching. The fallback is a PYTHONPATH bootstrap module.
- Docs created: SPECIFICATION.md, WORKPLAN.md, AGENTS.md, SKILLS.md.

## 2026-11-04 — Stage 1 finished: skeleton
- Package (MarimoCore lib, MarimoDesktop exe, tests), Info.plist, entitlements, `scripts/build_app.sh` (ad-hoc signed .app) all work.
- **Decision: Swift Testing, not XCTest.** With Command Line Tools only, `XCTest` is absent. `Testing.framework` exists but is off SwiftPM's search path, so `scripts/test.sh` passes `-F`/`-rpath` flags. Use `scripts/test.sh`, not bare `swift test`.

## 2026-11-04 — Stage 2 finished: environment + server manager
- Added AppPaths, ProcessRunner (line-streaming), PythonEnvironment (uv preferred, python -m venv fallback), PortAllocator, PIDRegistry (orphan reaping), MarimoServer (spawn + /health poll + token parse), AppModel and SetupView.
- 9 unit tests plus a real integration test (`MARIMO_INTEGRATION=1`) that builds a venv, installs marimo and starts a server. All pass.
- **Decision: build products go to `~/.cache/marimodesktop-build`** (`--scratch-path`). The repo sits on a shared-folder volume with unreliable mtimes, which made SwiftPM fail with "input file was modified during the build".
- **Protocol verified live (marimo 0.25.2):** kiosk WS `ws://127.0.0.1:P/ws?session_id=…&file=<abs path>&kiosk=true` receives `kernel-ready` (resumed:true), then `variables` `{name, declared_by, used_by}` and `variable-values` `{name, value, datatype}`, all wrapped as `{"op":…,"data":{…}}`. The primary session must connect first. HTTP API calls need the `Marimo-Server-Token` header (token embedded in index HTML as `serverToken`) and a `Marimo-Session-Id` header.
- Missing uv and python is reported with install guidance. We do not auto-download uv (out of scope).

## 2026-11-04 — Stage 3 finished: tabs, web view, New / Open / Save As
- NotebookSession (server + WKWebView per tab, origin-locked), glass tab bar, welcome screen, File menu (New ⌘N, Open ⌘O, Open Recent, Close Tab ⌘W, Save ⌘S, Save As ⇧⌘S), ⇧⌘[ / ⇧⌘] tab switching, tab restore (`session.json`).
- **Decision: Save = send ⌘S to marimo's own frontend** (JS KeyboardEvent). The frontend holds the unsaved cell edits, and the HTTP save API needs every cell's code. Marimo autosaves after 1 s by default, so this is belt-and-braces. **Not yet verified visually** (the VM gives no screen capture); see Known issues.
- **Decision: Save As = save, copy the file with FileManager, relaunch the tab's server on the new path.** Alternative: the `/api/kernel/rename` endpoint keeps the live session, but it needs the web view's session id, which we don't hold. Cost: the kernel restarts after Save As.
- **Decision: no dirty-dot or unsaved-changes prompt for saved files**, given autosave. Untitled notebooks that differ from the template prompt (Save As / Discard / Cancel) on close, because they have no home yet. SPECIFICATION FR-TAB-2/4 amended accordingly.
- **Bug found by smoke test:** AppKit synthesised File ▸ New on a cold launch, creating a stray Untitled file. Fixed with `applicationShouldOpenUntitledFile = false` and an `isReady` guard. Multi-file Finder open was losing all but one file with `onOpenURL`. Moved to `application(_:open:)` with a pending queue for cold launches.
- **Smoke-tested for real:** the app builds a venv in Application Support, launches a server per file, and the WKWebView holds live connections to it. Quitting leaves zero marimo processes.
- Note: the venv path contains a space ("Application Support"), so pip's console-script shebang is invalid and a `/bin/sh` trampoline runs. It works, and the PID tracked is the real server because the trampoline execs.

## 2026-11-04 — Stage 4 finished: variable browser
- VariableTable (pure message folding; fixtures from live marimo), VariableMirror (URLSessionWebSocketTask kiosk client with retry loop), inspector UI (filter, type badge, cell number, click-to-copy, empty states), ⌥⌘I toggle.
- **Integration test passes against real marimo:** a test plays the primary web view, runs a cell via `/api/kernel/run`, and the Swift mirror receives `answer = 42 : int`.
- **Decision: start the mirror from `WKNavigationDelegate.didFinish`** so the primary session exists before the kiosk joins (kiosk first would be rejected). The mirror also retries every second, so a transient failure heals itself.
- Variables are sorted by name with underscore-private names last. Value previews are marimo's own strings, so large objects are already truncated server-side.
